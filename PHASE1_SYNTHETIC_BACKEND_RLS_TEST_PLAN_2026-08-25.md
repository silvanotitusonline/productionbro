# Phase 1 — Synthetic Backend Authorization and RLS Test Plan

## Objective and boundary

This plan validates the reconstructed RTC Community backend only in the authorized zero-data non-production project `eqwstpdjoineycrkhpht`. Every authenticated call must use a real JWT obtained from an isolated synthetic account; every administrator assertion must deliberately distinguish a fresh password session at `aal1` from a real TOTP-upgraded session at `aal2`. The test harness must never embed, print, commit, or upload a password, bearer token, publishable key, TOTP secret, service-role credential, production identifier, signed URL, or Firebase material.

The scope is **backend contract and authorization evidence**, not release approval. No scheduler, cron extension, pg_net endpoint, Vault secret, FCM credential, alert dispatcher, recovered Edge Function, or `ops_retry_failed_community_alert` invocation is allowed in this phase.

## Synthetic-domain data discipline

Only the smallest data necessary for each proof may be created. All titles, bodies, descriptions, reasons, localities, and metadata must contain a deterministic `SYNTHETIC-RTC-20260825` marker. The runner must use an ignored owner-only state file to store generated UUIDs for the current run; it must not write these UUIDs into Android source, configuration, or the committed test plan. Where a test requires a role transition, it must restore the baseline role before reporting the result.

## Pass criteria and release constraint

A passing test must demonstrate the expected response status and semantic result. An expected-denial test passes only when the database or RPC rejects the request at the server boundary; a hidden UI state, client-side refusal, empty optimistic model, or mocked response is not evidence. A positive test passes only when the authorized identity receives the documented result and the corresponding audit/state side effect is observable through a guarded contract or structural check.

Completion of this plan does not mean that the Android application is production-ready. It is a prerequisite for the next Android route-authorization and persistence repairs, and it does not waive media, FCM, dispatcher, Edge Function, Concept 6, accessibility, performance, test-suite, or release-gate work.

## Execution checkpoint — Community Storage draft-owner policy and cleanup

The new `community-media-storage` slice completed **30 passing checks** against the authorized zero-data non-production project. It used one bounded embedded 1×1 PNG only at the exact ignored-state path `RESIDENT_A/marked-draft/synthetic-storage-policy.png`; no object bytes, signed URL, token, identifier, or media metadata was retained in source-controlled evidence. The slice first re-ran the existing public and direct-RLS smoke checks, then proved that Resident B cannot upload under Resident A’s draft path and Resident A cannot upload under a nonexistent draft path.

The initial slice revealed an Android-used Storage contract defect: the pinned client removes media through the bucket-level Storage API with a JSON `prefixes` array, and this operation requires the requesting author to select the target object. The isolated source-controlled migration `allow_community_draft_owner_storage_cleanup`, platform version `20260825163521`, added only an authenticated author’s own active `DRAFT`-post-path selection policy. It does not permit anonymous, cross-resident, staff-bypass, or otherwise ineligible media access. Its narrow purpose is protected author draft preview and reliable Storage API cleanup; published/locked viewer access remains governed by registered `community_post_media` visibility.

The rerun proved that Resident A can upload and read the bounded marker within their own active draft path, while Resident B cannot read it. Resident B’s bucket-level delete request returned an HTTP acknowledgment but the author-visible Storage metadata remained present, proving no cross-owner mutation. Resident A then deleted the marker through the pinned-client-compatible Storage API, and the metadata endpoint returned denial afterwards, confirming physical object removal. The runner adds a best-effort `finally` cleanup that repeats this exact owner-and-marker-path removal and verifies metadata absence if any later assertion interrupts the normal path. The post-migration advisor retained **0 `rls_enabled_no_policy` findings** and the existing **50** guarded authenticated `SECURITY DEFINER` review warnings; this storage change introduced no new advisor category. This is backend policy evidence only and does not alter the overall **NO-GO** production readiness status.
